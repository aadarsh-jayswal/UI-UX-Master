# Discovery interview

Re-authored from Johnathan Mo's `interview` skill (MIT; see licenses). Use only when a user is available to answer and the missing answers would change the deliverable. With no user available, write the spec with labelled assumptions and list the open questions instead.

1. Read the request and any existing product material first. Do not ask what the material already answers.
2. Ask in short rounds of non-obvious questions that change decisions: the primary task and success condition, constraints (platform, stack, content, legal or payment rules), edge states (no availability, conflicts, offline, session expiry), accessibility needs, tradeoffs the user cares about, and what must not change. Skip questions whose answer would not change the design.
3. Offer a recommended answer with each question when a sensible default exists, so the user can accept quickly.
4. Stop when the remaining unknowns no longer change the spec. Record each answer as a decision and each unanswered question as an assumption or open decision.
5. Write the spec where the user's project keeps plans (ask if unclear) and state the path. Follow the design-specification section of the [quality bar](quality-bar.md).

Use the host's question tool when one exists; otherwise ask in the conversation. Do not invent answers on the user's behalf.
