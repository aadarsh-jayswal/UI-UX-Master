# Existing product improvement

For a clear bounded fix, start directly with its owner: ui-design-toolkit, fixing-accessibility, or animate. No preliminary whole-product audit is required.

For evaluation, improve-ui selects a coherent surface and labels its evidence. Critique can use rendered heuristics; an audit needs a governing contract, runtime connection, and supported correction. Accessibility or motion audits add their specialist only when requested or necessary to the stated scope.

For redesigns, inspect the original brand imagery, hero/section narrative, hover navigation, interactive details, and scroll choreography. Preserve successful identity and behavior while developing the new direction. Use animate proactively when motion carries the experience. Compare rendered interactions as well as screenshots; a cleaner static layout does not by itself establish an improvement.

Prioritize verified root corrections and retain intentional product decisions. Use [findings](../templates/findings.md), then a self-contained [plan](../templates/implementation-plan.md) only for selected/requested changes. Audit stays read-only. If the user already requested implementation, pass the scoped plan to the appropriate writer without redundant authorization. If a product choice remains unresolved, ask only that choice.

Implementation rechecks evidence for drift, reuses actual tokens/components, edits authorized scope, and verifies affected behavior. A shared-system change belongs to design-system for the contract and the relevant writer for consumer code. Do not run two owners against the same file concurrently or bounce the task back through the router repeatedly.

Finish with implemented versus proposed work, checks/results, and any remaining visual/device/integration limitations. Reconcile older plans only against current evidence, never because their title sounds complete.
